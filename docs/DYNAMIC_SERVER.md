# 문연 동적 서버 운영 전환 안내

기준일: 2026-11-20. 현재 소스를 기준으로 한 설명과 실행 계획이다. 기존 Docker 운영 전환 계획을 보존한 문서다. 2026-11-20에 실제로 배포한 AI 없는 홈서버 시안은 [별도 배포 기록](PREVIEW_DEPLOYMENT.md)을 따른다.

## 이미 동적 서버가 구현되어 있다

현재 React 화면은 `/api`로 요청을 보내고, Node.js가 로그인·과제·학습 대화·제출·구술평가를 처리해 SQLite에 저장한다. `dist/` 파일만 정적 호스팅에 올리면 이 API와 저장 기능은 실행되지 않는다. GitHub 저장소 업로드 역시 서비스 배포와 다르다.

```text
브라우저의 React 화면
       │ HTTPS / 같은 도메인
       ▼
Caddy :443 — 인증서·프록시
       ▼
Node.js :4311 — 정적 화면 + /api + /healthz
       ├── SQLite 영속 볼륨 — 계정·세션·과제·대화·제출·평가
       └── AI 제공자 — 서버에서만 API 키 사용
```

개발 시 Vite는 화면을 제공하고 `/api`만 4311 포트의 서버로 전달한다. 운영 시에는 Node.js가 빌드된 화면까지 제공하므로 Vite 개발 서버를 외부에 노출할 필요가 없다.

## 첫 운영 구성 제안

현재 단일 과제 MVP를 시험할 때는 Linux 서버 한 대에 기존 Docker Compose의 앱 1개와 Caddy를 실행하는 구성이 코드 변경이 가장 적다. SQLite는 영속 볼륨을 사용하고 같은 DB를 여러 앱 인스턴스가 함께 사용하는 구성은 피한다. 서버 규모와 비용은 예상 학생 수·AI 사용량·동시 요청 측정 후 정한다.

1. 서버·도메인·모델 제공자와 데이터 전송 범위를 결정한다.
2. 서버에 Docker Engine·Compose를 준비하고 도메인 DNS를 연결한다. 외부 80·443은 Caddy로 연결하고 앱 4311 포트는 내부에 둔다.
3. 저장소를 내려받아 `.env.example`을 `.env`로 복사한다. 도메인과 실제 모델 기본 주소·모델명·필요한 키를 설정한다.
4. `docker compose build app` 후 [README의 운영 계정 생성 절차](../README.md#첫-배포)에 따라 개별 교수자·학생 계정을 발급한다. 체험 계정 DB는 운영에 그대로 사용하지 않는다.
5. `docker compose up -d --wait`로 시작하고 `https://도메인/healthz` 및 로그인 화면을 확인한다.
6. 학생의 학습·제출부터 교수자의 질문 확정·평가까지 실제 모델과 함께 확인한다.
7. 컨테이너 재시작 후 자료가 남는지, 별도 저장소에 백업하고 새 DB로 복구할 수 있는지 확인한다.

구체적인 비밀번호 입력·백업·복구 명령은 기존 README에 유지했다. 실제 도메인·서버·비용이 결정되기 전에는 외부 배포를 실행하지 않는다.

## 설정에서 주의할 점

| 설정 | 의미와 확인 사항 |
| --- | --- |
| `MUNYEON_DOMAIN` | Compose/Caddy용 도메인. `https://`와 경로를 제외한다. |
| `MUNYEON_ORIGIN` | Compose가 도메인으로부터 설정하는 HTTPS 출처. 운영 쓰기 요청의 Origin을 검사한다. |
| `MUNYEON_AI_URL` | `/chat/completions` 앞의 기본 주소. 컨테이너 안에서 접근 가능해야 한다. |
| `MUNYEON_AI_MODEL`, `MUNYEON_AI_KEY` | 실제 제공자의 모델명과 필요 시 키. 키는 Git에 넣지 않는다. |
| `MUNYEON_AI_OUTPUT_LIMIT_FIELD` | 제공자에 맞는 토큰 제한 필드. 실제 제공자로 검증한다. |
| `MUNYEON_AI_DAILY_LIMIT` | 인스턴스 전체의 24시간 호출 한도. 기본 120회, 운영 모드에서 적용. |
| `MUNYEON_DB_FILENAME` | Compose 영속 볼륨 내부 DB 파일명. 로컬 직접 실행 시에는 `MUNYEON_DB`가 경로다. |

컨테이너의 `127.0.0.1`은 해당 컨테이너다. `.env.example`의 로컬 모델 주소를 운영 컨테이너에서 그대로 쓸 수 있다고 가정하면 안 된다. Compose는 명시된 `environment` 항목을 통해 값을 전달하므로 `.env`에 새 변수를 적기만 하면 앱에 전달되는 것은 아니다.

현재 운영 모드에는 계정당 시간당 20회 모델 호출, 응답 최대 1,600토큰, 로그인 시도 제한이 있다. 비용 상한은 호출 횟수만으로 정확히 계산되지 않으므로 실제 토큰 사용량과 제공자 청구도 확인해야 한다.

## 서비스 범위를 넓힐 때 필요한 개발

- **여러 강좌·과제:** `courses`, `enrollments`, `assignments`를 만들고 대화·제출·질문·평가를 과제와 연결한다. 학생 제출의 고유 조건을 학생 1명에서 `(assignment_id, student_id)`로 바꾼다. 기존 데이터 이전도 필요하다.
- **권한 분리:** 교수자에게 모든 제출물을 보여주는 현재 구조를 강좌 소유권·담당자·수강 등록 기준으로 제한한다.
- **초안·재제출:** 초안 저장 API와 제출 버전·마감·재제출 정책을 만든다. 제출 시점 지침 스냅샷은 보존한다.
- **운영 편의:** 계정·명단 관리 화면, 성적 내보내기, 보존 기간과 삭제 절차, 오류 모니터링과 자동 백업을 추가한다.
- **규모 확대:** 부하 측정 후 필요하면 PostgreSQL로 이전한다. 앱을 여러 대로 늘릴 때 세션·호출 제한·마이그레이션·백업도 함께 설계한다.
- **AI 경험:** 실제 모델 지침 준수 평가, 지연·실패 처리 개선, 필요 시 스트리밍과 비동기 작업을 검토한다. 현재는 전체 응답을 받은 뒤 표시한다.
- **학교 연동:** 학교가 허용하는 인증·외부 도구 연동 방식부터 확인한다. 현재 `X-Frame-Options: DENY`와 운영 CSP의 `frame-ancestors 'none'`은 iframe 표시를 막으므로 LMS 삽입을 위해서는 승인된 출처와 인증 흐름에 맞춘 검토가 필요하다.

## 운영 완료 확인 기준

HTTPS·쿠키·권한, 실제 모델 요청, 학생 간 데이터 분리, 제출·평가 보존, 재시작, 백업 복구를 실서버에서 확인해야 한다. 이번 로컬 통합 테스트는 이를 위한 기반이지만 실제 서버의 네트워크·인증서·성능 검증을 대신하지 않는다.
