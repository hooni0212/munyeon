# 문연 MVP 백엔드·화면 연동 명세

2026-11-20 · 구현 전 설계안

교수자는 과목별 AI 설정과 과제별 활용 기준을 등록한다. 학생은 과제 전용 AI와 대화하고, 최종 결과물에 AI 활용 보고서를 붙여 제출한다. 교수자는 보고서의 문단에서 원본 대화와 학생 설명을 확인하고, 이 근거를 바탕으로 학생의 이해와 판단을 묻는 질문을 준비한다.

## 1. 현재 코드와 개발 범위

| 영역 | 현재 저장소 | 이번 MVP에서 필요한 작업 |
| --- | --- | --- |
| 계정과 권한 | 교수자·학생 계정, 쿠키 세션, 역할 검사 | 과목 소유권과 수강 명단을 도입하고 하위 리소스까지 접근 범위를 검사 |
| 과목과 과제 | `assignment` 테이블의 `id=1`에 과제 설정 한 건 저장 | 과목·과제 다중 등록, 마감, 공개 상태, 과제별 활용 기준, 기준 버전 관리 |
| 과제 AI | 지침과 최근 대화를 보내는 모델 어댑터. 시안의 모델 호출 기본값은 비활성 | 과제 범위 대화, 예시 Q&A와 자료 발췌 반영, 기준 확인 항목과 응답 처리 기록 |
| 제출과 근거 | 학생당 텍스트 제출 한 건. 공유 답변·자기보고 한 건을 문단에 연결 | 과제당 학생별 초안, 텍스트 파일 입력, 보고서 생성, 여러 근거 연결, 문서·보고서 동시 제출 |
| 교수자 검토 | 제출물 목록, 본문, 공유 발췌와 수동·AI 추천 질문, 구술평가 저장 | 수강 명단 기반 제출 현황, 보고서와 원본 근거 열람, 확인 필요 표시, 근거가 있는 질문 선택·수정 |

기존 Node.js·SQLite·React 구성을 사용한다. 현재 코드의 동작은 [프로젝트 현황](PROJECT_STATUS.md), [`server/app.js`](../server/app.js), [`server/store.js`](../server/store.js), [`server/model.js`](../server/model.js)를 기준으로 한다. 아래 데이터 모델과 `/api/v1` 경로는 개발 대상이다.

### MVP에서 사용할 기본안

- 교수자 한 명이 과목을 관리하고, 기존에 발급된 학생 계정을 수강 명단에 추가한다. 과목 하나에 과제 여러 개를 만들 수 있다.
- 제출물과 강의자료는 UTF-8 `.txt` 파일 또는 직접 입력한 텍스트부터 지원한다. 화면에서 파일을 읽어 `fileName`과 `text`를 JSON으로 보낸다. 파일당 입력 한도는 UTF-8 기준 64 KiB로 제안하며 서버에서도 검사한다. 이미지형 PDF, DOCX, 원래 문서 서식 보존은 후속 범위다.
- 과제 공개 시 교수자가 설정한 과목 AI 지침, 예시 Q&A, 강의자료 버전, 과제 기준을 묶어 고정한다. 이후 과목 설정 수정은 다음에 공개하는 과제부터 반영한다. 진행 중인 과제의 기준 변경과 재제출 정책은 후속으로 논의한다.
- 교수자는 제출 후 보고서에 연결된 원본 대화와 해당 과제의 기준 확인 항목에 연결된 대화만 열람한다. 학생에게 대화가 저장되는 범위와 교수자 공개 범위를 채팅 시작 전에 안내한다.
- 2차 검증의 MVP 완료 지점은 교수자의 질문 준비다. 추천 질문을 선택·수정하거나 직접 질문을 추가한 뒤 대면에서 사용할 수 있다. 서비스 내 학생 답변, 결과 공개, 평가 이력 확장은 P1로 둔다.
- iCampus, 학교 SSO, 모델 파인튜닝은 현재 범위에서 제외한다. 기존 배포의 AI 비활성 기본값은 유지하며, 개발과 시연은 합성 데이터와 모의 모델로 검증한다.

## 2. 권한과 데이터 모델

교수자는 자신이 관리하는 과목, 학생은 자신이 등록된 과목의 공개 이력이 있는 과제에 접근한다. 마감·조기 종료 또는 본인 최종 제출 이후에는 학생에게 과제·대화·제출물을 읽기 전용으로 제공한다. 대화·초안·제출물은 `assignmentId`와 학생 ID를 함께 확인한다. 교수자 상세 조회는 제출 ID에서 과제와 과목까지 따라가 소유권을 확인한다. 자료, 보고서 항목, 대화, 추천 질문, 작업 상태도 같은 검사를 적용한다. URL이나 요청 본문에 있는 학생 ID만으로 접근을 허용하지 않는다.

| 엔터티 | 주요 필드와 규칙 |
| --- | --- |
| `users`, `sessions` | 기존 계정·세션 구조 재사용. `teacher`, `student` 역할 유지 |
| `courses`, `course_enrollments` | 과목 `name`, `ownerId`. 활성 수강 행은 `(courseId, studentId)`로 유일. 명단 변경 시 이후 접근 권한을 재검사 |
| `course_ai_settings`, `course_materials`, `course_examples` | 학습 목표, 응답 지침, 자료 이름·본문·버전, 예시 질문·모범 답변 쌍. 자료는 과목에 귀속하고 수정 시 새 버전 생성 |
| `assignments`, `assignment_versions` | 과목 ID, 제목, 본문, `deadlineAt`, `draft/published/closed`. 공개 버전에 AI 설정, 자료 버전 ID, 안내 문구, 활용 기준을 고정 |
| `assignment_ai_rules` | 공개 버전 내 `ruleId`, 단계 `stage`, 활동 `activity`, 적용 `decision: allowed/restricted`, 학생에게 보여줄 안내와 제한 시 대체 도움. 미설정 조합은 `unspecified`로 응답 |
| `chat_turns` | `assignmentId`, `studentId`, `assignmentVersionId`, `clientRequestId`, 단계·활동, 질문·답변, 상태, 생성 시각. 동일 과제·학생·요청 ID의 중복 저장 방지 |
| `policy_events` | 대화 ID, 공개 버전·규칙 ID, `matchType`, 조치, 확인 상태, 생성 시각, 교수자 메모·확인 시각. 제출물 유사도와 별개인 과제 채팅 기록 |
| `submission_drafts`, `draft_versions` | 과제·학생당 초안 한 건. 버전마다 제목, 입력 방식, 파일명, 정규화한 본문과 문단 목록 보존. 문단 ID는 해당 버전 안에서 고정 |
| `reports`, `report_items`, `evidence_links` | 보고서의 초안 버전·생성 상태·대화 범위. 항목의 `paragraphId`는 선택값. 근거에는 연결 출처(`system` 또는 `student`), 대화 ID, 공개된 발췌가 들어감 |
| `student_annotations` | 보고서 항목 ID, 활용 방식(`idea`, `direct`, `reworked`, `not_adopted`), 판단 설명, 이의 표시. 자동 분석 항목은 유지하고 학생 설명을 별도로 저장 |
| `submissions` | `(assignmentId, studentId)`당 한 건. 최종 초안 버전, 고정된 보고서, 과제 공개 버전, 제출 시각을 참조 |
| `review_flags`, `verification_questions` | 문단·보고서 항목의 교수자 확인 표시. 질문에는 작성 출처(`ai_suggested/manual`), 질문 문구, 근거 ID, 선택 여부와 버전 저장 |
| `jobs` | 보고서 생성·질문 추천 작업의 소유 범위, 입력 버전, 상태(`queued/running/succeeded/failed`), 재시도 정보 저장 |

제출물의 앵커는 `paragraphId`로, 기타 보고서 항목은 `reportItemId`로 찾는다. `검토 후 미반영` 항목은 `paragraphId=null`을 허용한다. 근거와 질문은 같은 과제·학생·제출 버전의 ID만 참조해야 한다. 사용자 수정이 들어가는 요청에는 `revision`을 사용하고 서버의 버전과 다르면 `409`를 반환한다.

## 3. 처리 흐름과 화면 상태

### 3.1 과제 공개와 AI 채팅

1. 과제를 공개하기 전에 제목·마감과 AI 활용 기준을 확인한다. 예를 들어 `planning + brainstorm`은 허용, `drafting + generate_submission`은 제한으로 설정한다. 단계 ID와 활동 ID는 서버의 과제 응답을 사용한다. 저장 시각은 UTC ISO 8601, 화면 기본 표시는 `Asia/Seoul`이다.
2. 학생이 보낸 메시지에는 선택한 `stage`와 `activity`를 포함한다. 서버는 공개 버전의 규칙을 조회한다. **명시적으로 제한된 요청**은 모델 답변 생성 전에 차단하고 대체 도움을 안내한다. 질문과 안내 답변, 대응 규칙은 `chat_turns`와 `policy_events`에 함께 저장한다.
3. 허용 모드의 자유 입력에서 제한 요청 가능성이 드러날 수 있다. 이 경우 모델 또는 서버 검사 결과는 `possible_match`로 기록한다. 검토에 충분한 구간과 규칙이 있는 경우에만 교수자에게 **기준 확인 필요**로 표시한다. 불확실한 요청에는 답안 대신 힌트나 확인 질문을 제공한다. 모델의 분류와 보고서 유사도로 위반을 확정하지 않는다.
4. 교수자는 항목의 요청, 당시 기준, 시스템이 제공한 답변을 비교한다. 상태는 `pending`(확인 필요), `confirmed`(교수자 확인), `dismissed`(확인 후 해제)로 저장한다. 학생 화면에서는 해당 요청에 적용된 기준과 시스템 조치를 확인할 수 있다. 제출물 검토 때 이 기록을 보여주되 자동 감점에 사용하지 않는다.

| 구분 | 기록 기준 | 화면 문구 예시 |
| --- | --- | --- |
| `explicit_restriction` | 선택한 활동이 공개 버전의 제한 규칙에 해당 | `제한된 요청 · 힌트로 안내` |
| `possible_match` | 자유 입력이 제한 규칙과 관련될 가능성이 있고 근거 구간을 특정할 수 있음 | `기준 확인 필요` |
| `unspecified` | 적용할 규칙이 없거나 근거가 부족함. 확인 항목을 생성하지 않음 | `이 활용 방식의 기준을 확인해 주세요` |

채팅 모델에는 서버 기본 지침, 고정된 과목·과제 지침, 예시 Q&A, 해당 과목 자료의 관련 발췌, 현재 학생의 같은 과제 대화, 새 질문을 제공한다. 자료·제출물·대화 내용은 참고 데이터로 취급한다. MVP 자료 참조는 해당 강의자료에서 관련 텍스트 조각을 고르는 방식으로 시작하고, 검색 품질 고도화는 P1에 둔다. 모델 연결이 꺼져 있거나 실패하면 화면에 상태를 반환하며, 학생 채팅은 같은 `clientRequestId`로 결과를 확인하거나 실패한 요청을 재시도한다.

### 3.2 초안, AI 활용 보고서, 제출

1. 서버에서 텍스트를 검사하고 문단을 나눠 초안 버전을 만든다. 초안 응답에 문단 ID와 표시 순서를 포함한다.
2. 보고서 생성 요청은 해당 **초안 버전과 분석 시작 때 완료된 과제 대화**를 묶어 작업을 만든다. 응답의 보고서 요약, 확인 필요 항목, 문단과 대화 연결을 검사한다. 존재하지 않거나 권한이 다른 ID를 모델이 반환하면 연결을 저장하지 않는다. 발췌 문구는 모델의 요약을 복제하지 않고 연결된 저장 원문에서 가져온다.
3. 자동 분석은 `similar`(AI 대화와 유사)과 `no_matching_record`(관련 기록 미확인)를 반환한다. 수정된 것으로 보이는 내용은 근거와 함께 분석 메모에 남긴다. 학생의 참고 표시는 근거·설명에 `student` 출처로 저장한다. 한 문단에 자동 결과와 학생 연결을 함께 보여줄 수 있다. 예를 들어 `관련 기록 미확인` 아래에도 `학생 직접 연결` 근거가 추가될 수 있다.
4. 학생은 문단 또는 미반영 항목에 대화 발췌를 추가·수정·제거하고 활용 방식과 판단을 적는다. 자동 연결이 잘못되었다고 판단하면 이의 이유를 남긴다. 교수자에게는 자동 분석과 학생의 설명을 함께 보여준다.
5. 초안 본문을 수정하면 기존 보고서는 `stale` 상태가 된다. 이후 새 대화가 완료되어도 분석 범위 갱신을 요청한다. 초안이 그대로면 다시 분석할 때 학생 설명을 유지하고, 초안이 바뀌면 이전 설명을 열람해 해당 문단을 확인한 뒤 옮길 수 있게 한다.
6. 제출 요청에서 과제의 마감, 본인 여부, 일치하는 문서·보고서 버전, 제출 중복을 검사한다. 한 트랜잭션에서 최종 제출물과 보고서 내용을 고정한다. 결과가 저장된 뒤 같은 요청을 다시 보내면 기존 성공 응답을 반환한다. 같은 요청 ID로 내용이 바뀌면 `409`를 반환한다.

| 보고서 상태 | 학생 화면 동작 |
| --- | --- |
| `not_started` | 안내와 `보고서 생성` 버튼 표시 |
| `processing` | 진행 표시. 작업 상태를 조회하면서 현재 선택한 버전만 갱신 |
| `ready` | 자동 근거 확인·학생 설명 보완·제출 가능 |
| `failed` | 초안 유지, 재시도 또는 수동 보고서 선택 |
| `manual_only` | 지정 AI 기록이 없거나 모델 장애 시 수동 설명·제출 가능. 자동 분석 미실행을 표기 |
| `stale` | 문서 또는 분석 대상 대화가 바뀌었다고 안내하고 보고서를 다시 준비하도록 표시 |

`관련 기록 미확인`은 해당 과제의 분석 범위에서 연결할 대화를 발견하지 못했다는 표시다. AI 사용 여부나 문장 작성 주체에 대한 판단은 포함하지 않는다. `manual_only` 보고서와 학생이 추가한 미반영 항목의 자동 분석 상태는 `null`이다.

### 3.3 교수자 1·2차 검토

- **1차 검토**는 수강 명단에 제출 상태를 붙여 시작한다. 제출 학생 선택 시 최종 제출물, AI 활용 보고서, 확인 표시와 기준 확인 항목을 조회한다. 문단·항목을 클릭하면 오른쪽에 자동·학생 연결을 구분해 원본 대화와 설명을 내보낸다. 제출물이 없는 학생에게는 미제출 상태를 표시한다.
- **2차 질문**은 고정된 제출물과 보고서의 공개된 근거를 사용한다. 모델 출력에는 질문 문구와 `paragraphIds`, `reportItemIds`, `evidenceLinkIds` 중 해당하는 근거를 포함한다. 서버가 소속과 유효성을 확인한 질문만 보여준다. 교수자는 질문의 근거를 열고, 문구를 편집하거나 직접 질문을 작성하고 선택할 수 있다. 문구 편집 이력에 최초 작성 출처를 유지한다.
- 2차 질문의 좋은 예는 “왜 이 기준을 선택했고, 어떤 사례에서는 다른 기준이 더 적절할까요?”처럼 학생이 한 판단을 묻는 것이다. 대화 근거가 없으면 해당 제출 문단이나 학생 설명을 바탕으로 묻는다. 추천이 실패해도 직접 작성 기능을 제공한다.

## 4. UI 연결용 API 계약

기존 `GET /api/session`, `POST /api/login`, `POST /api/logout`과 같은 세션을 사용한다. 아래 경로는 `/api/v1` 기준이다. 화면에 보이는 상태 라벨은 안정적인 코드에서 매핑한다. 목록 요청은 페이지 크기와 커서(`limit`, `cursor`)를 받고 `{ items, nextCursor }`를 반환한다. 과목·과제·사용자·문단 등의 ID는 양의 정수로 통일한다.

| 화면·작업 | 메서드와 경로 | 주고받는 내용 |
| --- | --- | --- |
| 공통 과목 목록 | `GET /courses` | 사용자에게 허용된 과목 ID와 과목명 |
| 교수자 과목 관리 | `POST /courses`, `PATCH /courses/{courseId}` | 과목명 생성·수정 |

| 교수자 과목 AI 설정 | `GET/PUT /courses/{courseId}/ai-settings` | 학습 목표, 응답 지침, 예시 Q&A 목록, 설정 버전. `PUT`은 예시 쌍을 포함한 설정 전체 저장 |
| 교수자 강의자료 | `GET/POST /courses/{courseId}/materials`, `PUT /courses/{courseId}/materials/{materialId}` | 자료 목록, 이름·본문 추가, 새 자료 버전 저장 |

| 교수자 과제 관리 | `POST /courses/{courseId}/assignments`, `PATCH /assignments/{assignmentId}`, `POST /assignments/{assignmentId}/publish`, `POST /assignments/{assignmentId}/close` | 초안 생성·수정, 제목·내용·마감·규칙 공개, 조기 마감 |
| 학생 과제 AI | `GET/POST /assignments/{assignmentId}/chat` | 본인 대화 목록, `clientRequestId/stage/activity/text`, 응답·조치·안내 |
| 학생 제출 초안 | `GET/PUT /assignments/{assignmentId}/draft` | `title/text/fileName/revision`, 현재 문단 목록, `draftVersionId` |
| 학생 보고서 준비 | `GET /assignments/{assignmentId}/report`, `POST /assignments/{assignmentId}/report/generate`, `POST /assignments/{assignmentId}/report/manual` | 현재 보고서 및 항목, 지정 버전의 분석 요청, 수동 보고서 준비. 생성 요청은 `202`와 `jobId` 반환 |

| 교수자 제출 상세 | `GET /submissions/{submissionId}`, `GET /submissions/{submissionId}/evidence/{evidenceLinkId}` | 고정된 본문·보고서·확인 표시. 적용 규칙과 관련 발췌를 포함한 `policyEvents` 목록, 보고서에 연결된 원본 대화 발췌 |
| 교수자 1차 확인 | `PUT /submissions/{submissionId}/review-flags`, `PATCH /submissions/{submissionId}/policy-events/{eventId}` | `paragraphId` 또는 `reportItemId`에 확인 표시와 메모 저장, 기준 확인 항목의 상태 변경 |
| 교수자 2차 질문 | `GET/POST /submissions/{submissionId}/questions`, `PATCH /submissions/{submissionId}/questions/{questionId}`, `POST /submissions/{submissionId}/questions/suggest` | 목록·직접 작성·문구 수정·선택 상태 변경·추천 작업 요청 |
| 작업 진행 조회 | `GET /jobs/{jobId}` | 본인 요청의 처리 상태·결과 리소스 ID·재시도 가능한 오류 |

학생이 근거를 선택할 때는 본인의 채팅 목록을 사용한다. 제출물 상세에서 질문이나 근거로 이동할 때는 `submissionId`, 선택된 `reportItemId` 또는 `paragraphId`, `evidenceLinkId`를 화면 상태로 유지한다. 과목·과제·학생이 바뀌면 이전 상세 요청의 응답을 현재 화면에 적용하지 않는다.

과제 공개 설정의 입력 필드는 `title`, `instructions`, `deadlineAt`, `rules[]`로 시작한다. 규칙은 `stage`, `activity`, `decision`, `description`, `alternativeHelp`를 갖는다. 과목 AI 설정은 `learningGoal`, `instructions`, `examples[]`를 받고 예시마다 `question`, `answer`를 저장한다. 보고서 분석과 질문 추천은 동일한 입력 버전의 작업이 진행 중이면 기존 작업 ID를 돌려준다. 뒤늦게 끝난 작업은 생성 당시 버전에만 연결한다.

### 화면에서 공유할 데이터 예시

교수자 상세 응답의 보고서 항목 예시다. `evidenceLinks`와 `annotations`는 같은 항목 안에서도 별도로 보여준다.

```json
{
  "id": 204,
  "paragraphId": 52,
  "analysisStatus": "no_matching_record",
  "evidenceLinks": [{ "id": 308, "source": "student", "turnId": 176 }],
  "annotations": [{
    "id": 401,
    "usageType": "reworked",
    "explanation": "두 화면에서 같은 항목을 찾는 데 걸린 시간을 비교하도록 바꿨어요."
  }],
  "reviewFlag": false
}
```

API 오류는 기존 `error` 메시지를 유지하고 식별용 `code`를 붙인다. 로그인 필요 `401`, 역할 불일치 `403`, 소속 밖 리소스 또는 없는 ID `404`, 오래된 편집 버전·마감·중복 `409`, 입력 오류 `400/422`, 용량 초과 `413`, 호출 한도 `429`, 모델 일시 오류·비활성 `502/503`을 사용한다. UI에서 `REVISION_CONFLICT`, `DEADLINE_PASSED`, `REPORT_STALE`, `AI_DISABLED`를 구분해 재조회·초안 보존·수동 보고서 등의 동작으로 연결한다.

## 5. 사용 시나리오와 인수 조건

기본 시연 데이터는 `창의융합적디자인 → 디자인 문제 해결 보고서`로 만들고, 학생은 제출한 김하윤·박서준과 미제출인 이유진을 둔다. 권한 검증에는 두 번째 과목, 별도 교수자, 두 과목에 등록된 학생 한 명을 추가한다. 예시 데이터는 운영 DB와 분리한다.

| 시나리오 | 사용자 행동 | 완료 기준 |
| --- | --- | --- |
| 과제 공개 | 교수자가 참고 자료와 예시 Q&A를 저장하고 구상은 허용, 본문 대필은 제한으로 과제를 공개한다. | 수강 학생이 과제·마감·기준을 본다. 미수강 학생은 접근할 수 없다. 이후 과목 설정을 바꿔도 공개된 과제의 기준은 고정된다. |
| 제한된 요청 | 학생이 ‘제출문 대필’에 해당하는 활동을 골라 채팅한다. | 안내 또는 힌트가 표시되고 대화·적용 규칙·조치가 저장된다. 제출 후 담당 교수자의 기준 확인 항목에서 근거를 볼 수 있다. |
| 학생이 누락 근거 보완 | 김하윤이 검토 계획 문단에 기존 대화를 연결하고 무엇을 바꿨는지 적어 제출한다. | 자동 분석과 학생 직접 연결이 둘 다 보존된다. 교수자가 해당 문단을 눌렀을 때 오른쪽에 연결된 원문과 학생 설명이 표시된다. |
| 제안을 검토하고 미반영 | 학생이 AI의 유사도 점수 제안을 검토했지만 최종안에서 제외한 이유를 남긴다. | 문단을 선택하지 않고도 미반영 이유와 대화를 공유한다. 교수자 보고서에서 독립된 항목으로 열린다. |
| 근거 기반 2차 질문 | 교수자가 해결 제안의 원본 대화를 읽고 추가 확인으로 표시한 뒤, 추천 질문을 수정한다. | 질문에서 근거 문단과 대화로 이동할 수 있다. 수정한 문구와 선택 상태가 새로고침 후 유지된다. 추천 실패 시에도 직접 작성이 된다. |
| 초안 변경과 장애 | 학생이 보고서 생성 뒤 본문을 바꾸고, 다시 생성할 때 모델 연결이 끊긴다. | 이전 보고서로 제출할 수 없다. 최신 초안은 유지되고 재시도 또는 수동 보고서로 마무리할 수 있다. |
| 과제/과목 격리 | 두 번째 교수자가 다른 과목의 제출 ID·근거 ID로 열람을 시도하고, 학생이 두 과제에 각각 제출한다. | 타 과목 열람이 실패한다. 같은 학생도 과제별 제출·대화·근거가 독립적으로 저장된다. |
| 중복 요청과 마감 | 학생이 제출 버튼을 두 번 누르거나 마감 후 저장된 초안으로 제출을 시도한다. | 마감 전 동일 요청은 한 건으로 처리한다. 마감 후 최초 제출은 오류와 함께 차단되고 초안은 남는다. |

## 6. 구현 순서와 운영 결정

1. **과목 경계부터 추가.** 기존 계정·세션을 유지하고 SQLite 스키마 버전을 도입한다. 과목, 명단, 과제, 과제 버전과 소유권 검사를 먼저 구현한다. 과거 DB에는 소유 교수자와 수강 명단 정보가 없으므로 백업 후 지정한 교수자·과목으로 매핑한다. 과거 공유 발췌의 원본 대화 ID를 확인할 수 없으면 기존 발췌임을 표시한다. 신규 과목 정보를 기존 공용 API로 노출하지 않는다.
2. **학생 입력과 교수자 기본 화면 연결.** 텍스트 초안·문단 ID, 마감·제출, 학생별 목록·본문을 먼저 붙인다. Figma 화면에 연결할 때 과목·과제·학생의 선택 상태와 로딩·빈 목록·미제출·마감 오류를 점검한다.
3. **채팅, 정책 기록, 보고서 연결.** 과제별 AI 지침, 명시적 제한 처리, 학생 보완, 자동 보고서와 원본 근거 조회를 구현한다. 작업은 DB에 저장하고 같은 버전의 중복 실행을 피한다. 외부 모델을 기다리는 동안 SQLite 쓰기 트랜잭션을 열어두지 않는다. 모델 장애 시 입력과 기존 보고서를 보존한다.
4. **질문과 전 과정 검증.** 추천과 직접 작성, 유효한 근거 링크, 교수자 확인 상태를 연결한다. 위 시나리오를 브라우저와 API 통합 테스트로 검증한다. 다른 과목 ID 주입, 마감 시각 경계, 중복 제출, 새로고침·서버 재시작, 모델의 잘못된 ID 반환을 포함한다.

실제 수업 전에 **교수자 공개 범위와 시점, 보관 기간·삭제 요청 처리 및 백업 반영, 외부 모델에 보낼 입력 범위**를 확정해야 한다. 대화나 과제 원문은 일반 서버 로그에 남기지 않고, 서비스 밖으로 보낼 때는 필요한 문단과 발췌만 선택한다. 연결 근거가 보관 정책에 따라 삭제되면 보고서·기준 확인 항목의 발췌 사본도 정리하고 링크 위치에 `원본 열람 기간 만료` 상태를 제공한다. 시연용 데이터에는 실제 학생 기록을 사용하지 않는다.

Figma 시안과 대조할 첫 항목은 **오른쪽 패널의 ‘원본 근거 / 기준 확인 / 2차 질문’ 진입점**, **학생의 근거 추가·이의 표시 UI**, **자동 분석 실패 시 수동 보고서 전환**이다. PDF·DOCX 도입, 작성 중 기준 변경, 학생 답변·평가 공개는 이 흐름을 확인한 뒤 결정한다.
